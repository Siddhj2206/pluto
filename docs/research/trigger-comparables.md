# Trigger & wake comparables — facts for pluto's triggers/wake grilling

Fetched 2026-10-04. Primary sources: vendor docs + source. celld facts from celld.dev docs and a shallow clone of `denoland/celld` @ `main` (local paths are clone-relative). Quotes are verbatim unless marked.

---

## 1. Cloudflare Durable Objects alarms

- **Shape:** one alarm per object. `setAlarm(ms)` overrides an existing alarm; `getAlarm()` returns ms or `null`, and "If `getAlarm` is called while an `alarm` is already running, it returns `null` unless `setAlarm` has also been called since the alarm handler started running"; `deleteAlarm()` unsets it. Handler is `alarm(alarmInfo)` with `retryCount` and `isRetry`. "Only one instance of `alarm()` will ever run at a given time per Durable Object instance."
- **Delivery:** "Alarms have guaranteed at-least-once execution and are retried automatically when the `alarm()` handler throws. Retries are performed using exponential backoff starting at a 2 second delay from the first failure with up to 6 retries allowed." Retries apply "only to the most recent `setAlarm()` call". `deleteAlarm()` inside the handler "may prevent retries on a best-effort basis, but is not guaranteed". Docs also warn to catch exceptions and re-arm if you want indefinite retry, because a long downstream outage exhausts the 6 retries.
- **Evicted / inactive object:** alarms are stored with the same replicated storage as the object (blog: "alarms are stored in the same distributed datastore that backs the Durable Object storage API"), so they are not lost to eviction. Lifecycle doc: "Assuming a Durable Object does not run, the first incoming request or event (like an alarm) will execute the `constructor()` of the Durable Object class, then run the corresponding function invoked." The 2022 launch blog: if the object is terminated, the `alarm()` handler "will be re-instantiated on another machine. Following a short delay, the `alarm()` handler will run from the beginning on the other machine." (Blog is older than the current 6-retry docs; docs win.)
- **Missed alarms / coalescing:** there is no queue of occurrences — the object holds a single alarm time, so a deadline that passes while the object is not running is delivered once when the object next runs. There is no per-interval catch-up.
- **Contrast with Cron Triggers:** "A Worker can have up to three Cron Triggers configured at once, but it can have an unlimited amount of Durable Objects, each of which can have an alarm set." Cron Triggers are not programmatic (dashboard/API config); alarms are scheduled from inside the object. The recommended way to run many schedules with one alarm is to store the schedule in storage and have `alarm()` process due events then re-arm.
- Links: [Alarms API](https://developers.cloudflare.com/durable-objects/api/alarms/), [Lifecycle of a DO](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/), [Use the Alarms API example](https://developers.cloudflare.com/durable-objects/examples/alarms-api/), [launch blog](https://blog.cloudflare.com/durable-objects-alarms/).

## 2. celld

celld implements **both** per-cell Durable Object alarms and Cloudflare-compatible **Cron Triggers** (Worker-level), and gives unusually explicit answers to the missed-run and wake questions.

- **Alarm durability & discovery (guarantees.md, "Alarm discovery and the wake format"):** SQLite stores "the alarm deadline, consumption, retry state, and installation identity. An alarm hint only causes celld to read SQLite. The hint does not authorize an alarm handler to run." Each committed alarm installation has a separate object under `wake/entries/`; "An alarm response waits for its publication PUT and the existing output proof. Updates within the same minute also require a new publication PUT." Cleanup uses conditional writes under `wake/retired/` so an old DELETE cannot remove a later installation. `wake/waker.json` "holds the advisory lease for the fleet's waker role". Waker tick defaults to 60 s (`CELLD_WAKER_TICK_MS`).
- **Who wakes what (docs, Alarms):** "A hibernated cell fires its alarm on the node that owns it. One node in the fleet holds the waker role at a time. The waker reads the due wake entries of the whole fleet, and it wakes only the cells whose owner node has stopped. Every other node wakes only its own hibernated cells, so the alarm load of the fleet does not queue on one node."
- **Routing/claim in code:** `crates/logic/types.rs` defines `WakeHintScope`: `Owned` = "Wake a dormant cell this node owns; ignore every other cell"; `Fleet` = "Probe ownership and take over a cell whose owner is gone." The waker's fleet-scope probe + ownership CAS is the claim step; SQLite, not the bucket entry, is delivery authority (`crates/celld/wake.rs`).
- **Alarm retry:** `crates/logic/alarm.rs`: `RETRY_CEILING = 6` counted failures, `BACKOFF_BASE_MS = 2_000`, delay `2s << min(retry, 6)`, abandon after the counted ceiling. Some failures (e.g. shed under pressure) back off but do not count toward the ceiling.
- **Cron Triggers:** schedule from Wrangler `triggers.crons`; parsed at deploy so malformed expressions stop deployment; 5-field Cloudflare dialect, minute resolution, UTC; celld refuses a few expressions CF accepts. "celld gives each deployment that declares `triggers.crons` one reserved cell, named from the class `.cron` and the script name. That cell carries the whole schedule of the script… so the reserved cell is what makes an occurrence run once for the fleet and not once for each node." Every node calls the cell once after its deployment loads; ownership CAS picks one owner; the others route to it; the call is idempotent. The cell hibernates between occurrences ("costs no isolate while it waits"), holds **one alarm row** armed at the earliest next occurrence across all expressions, and runs each matching expression's `scheduled(controller, env, ctx)` in sequence; "Two occurrences of one script never overlap."
- **Cron failure/retry:** docs: first failure arms a 4 s backoff, doubles per failure, "gives up on the occurrence after six failures"; a retry repeats only failed expressions; `controller.noRetry()` opts out. Source: `plan()` calls `alarm_retry(..., retry = 1, ...)` for cron, hence 4 s vs the generic 2 s base. "The next occurrence and the backoff compete for the one alarm row, and the earlier deadline wins. A retry therefore never delays a scheduled run and never replaces one." Retry state is in memory: "an eviction or an ownership move loses a pending retry and never the next occurrence."
- **Missed runs:** "celld runs one missed occurrence after downtime… the occurrences between the late one and now do not run. An application that must process every interval reads the interval from `controller.scheduledTime` and catches up in its own code." `scheduledTime` is the scheduled occurrence, never the attempt start.
- **Placement:** no placement promise; the occurrence runs on whichever node owns the reserved cell at the deadline; ownership can move on stop/drain/rebalance.
- Links: [celld docs](https://celld.dev/docs), [Cron Triggers](https://celld.dev/docs/services/cron-triggers), [Durable Objects / Cells](https://celld.dev/docs/services/durable-objects), [guarantees](https://github.com/denoland/celld/blob/main/docs/guarantees.md) (#alarm-discovery-and-the-wake-format); source: `crates/logic/{cron,alarm,wake,types}.rs`, `crates/celld/wake.rs`.

## 3. Fly Machines

- **Scheduled runs:** `config.schedule` is "Optionally one of `hourly`, `daily`, `weekly`, `monthly`. Runs Machine at the given interval. Interval starts at time of Machine creation." flyctl `--schedule` doc: "starts the Machine on a fuzzy `hourly`, `daily`, `weekly`, or `monthly` cycle. This is useful for running Machines that do a finite job, then exit. The Machine is started the first time when you run `fly machine run`, and again once per (approximate) hour, day, week, or month. For machines created with `fly machine create --schedule`, the first run will need to be manually started, since the cycle begins on the first machine start. Scheduled machines cannot be started via flyctl or Machines API commands, they will only run according to the schedule." Host-resource failure at trigger time returns an error: "It's up to you to build the appropriate level of redundancy into your apps." Suspend requires "No schedule configured."
- **Auto start on an incoming request:** Fly Proxy "waits for a request to your app… starts a stopped or suspended Machine in the nearest region (if there are any stopped or suspended Machines)… The proxy routes the request to the newly started Machine." Machines API: "For an application with a single Machine, all requests will be routed to that Machine. A Machine in the `stopped` state will be started up automatically when a request arrives." Default when unset: `auto_start_machines = true`; if explicitly false, "the proxy only routes traffic to Machines that are already running. If no Machines are running, the proxy does not start one and the request will fail."
- **Client-visible caveats:** "After a Machine starts, there may be a short delay before all proxy nodes recognize that it is running. During this time, requests sent to the Machine might fail if the proxy tries to route traffic too early." Autostop loop "runs every few minutes and stops at most one Machine per region per pass." No client-wait timeout for autostart is documented; the only start-related timeout found is `fly deploy`'s 5-minute wait for started state, and the Machines API `wait` endpoint (default 60 s), neither of which is a proxy setting.
- **stopped vs suspended:** stopped = exited; a restarted stopped Machine is "completely reset to their original state". suspended = Firecracker snapshot (CPU/memory/open files), resume "a few hundred ms" vs "~2+ seconds" cold boot; the next start "will attempt (but is not guaranteed) to resume"; snapshots are discarded by deploys, host migration, corruption, or maintenance, forcing a cold boot that keeps the rootfs; ≤2 GB recommended, no swap, no schedule; clock can lag after resume; TCP connections may survive; both states bill storage only.
- Links: [fly machine run — schedule section](https://fly.io/docs/flyctl/machine-run/), [Machines API resource](https://fly.io/docs/machines/api/machines-resource/), [Autostop/autostart](https://fly.io/docs/launch/autostop-autostart/), [How Fly Proxy autostop/autostart works](https://fly.io/docs/reference/fly-proxy-autostop-autostart/), [Suspend and resume](https://fly.io/docs/reference/suspend-resume/), [Machine states](https://fly.io/docs/machines/machine-states/).

## 4. E2B

- **Timeout:** every sandbox "defaults to 5 minutes if you do not set one"; `setTimeout()`/`set_timeout()` resets the clock from that moment to an exact value (can shorten or extend). `Sandbox.connect(timeout)` only extends: "the new expiry is the later of the current expiry and now plus the timeout you pass (default 5 minutes)" — it never shortens. Continuous runtime is capped by plan (1 h Hobby / 24 h Pro); pause+resume resets the window.
- **Connecting resumes paused sandboxes:** `connect()` "will automatically resume the sandbox, if paused" (documented). With `lifecycle.autoResume: true`, no explicit connect is needed: "a paused sandbox wakes up when activity arrives"; activity includes "both HTTP traffic and SDK operations" (commands.run, files reads/writes, requests to a tunneled app URL). Auto-resume requires `onTimeout: 'pause'` (not the default `'kill'`) and a memory snapshot; filesystem-only pauses cannot auto-resume. After auto-resume the sandbox gets a fresh timeout of at least 5 minutes (longer if originally longer); the pause/auto-resume cycle is persistent.
- **Scheduling:** E2B documents no cron/scheduled trigger for sandboxes; the only wake sources are SDK/HTTP activity (or explicit `connect()`). Paused sandboxes "are kept indefinitely" and never wake on their own.
- Links: [Sandbox lifecycle](https://docs.e2b.dev/sandbox), [Persistence](https://docs.e2b.dev/sandbox/persistence), [Auto-resume on request](https://docs.e2b.dev/sandbox/auto-resume), [FAQ: How long does a sandbox live?](https://docs.e2b.dev/faq/sandbox-lifetime).

## 5. systemd timers

- `OnCalendar=`: realtime (wall-clock) calendar expressions; timer subject to `AccuracySec=`. Sleep behavior: "When a calendar timer elapses while the system is sleeping it will not be acted on immediately, but once the system is later resumed it will catch up and process all timers that triggered while the system was sleeping. Note that if a calendar timer elapsed more than once while the system was continuously sleeping the timer will only result in a single service activation."
- `Persistent=`: "the time when the service unit was last triggered is stored on disk. When the timer is activated, the service unit is triggered immediately if it would have been triggered at least once during the time when the timer was inactive. Such triggering is nonetheless subject to the delay imposed by `RandomizedDelaySec=`. This is useful to catch up on missed runs of the service when the system was powered down. Note that this setting only has an effect on timers configured with `OnCalendar=`." Remove the timestamp with `systemctl clean --what=state`.
- `AccuracySec=`: defaults to 1 min. The timer elapses within a window starting at the configured time and ending `AccuracySec` later; "Within this time window, the expiry time will be placed at a host-specific, randomized, but stable position that is synchronized between all local timer units", to coalesce CPU wake-ups. `1us` for best accuracy.
- `RandomizedDelaySec=`: default 0; "Each timer unit will determine this delay randomly before each iteration, unless modified with `FixedRandomDelay=`"; the delay is added "on top of the next determined elapsing time or the service manager's startup time, whichever is later". It stretches events; `AccuracySec` coalesces. Combined: "first the randomized delay is added, and then the result is possibly further shifted to coalesce it with other timer events."
- Overlap: "in case the unit to activate is already active at the time the timer elapses it is not restarted, but simply left running."
- Links: [systemd.timer(5) man page](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html); exact text checked against [`man/systemd.timer.xml` @ main](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.timer.xml).

## 6. anacron (optional; coalescing missed cron runs)

- Design intent: "Unlike **cron(8)**, it does not assume that the machine is running continuously. Hence, it can be used on machines that aren't running 24 hours a day, to control daily, weekly, and monthly jobs that are usually controlled by cron."
- Coalescing: each job has "a period in days, a delay in minutes, a unique job identifier, and a shell command". For each job: "Anacron checks whether this job has been executed in the last n days… If not, Anacron runs the job's shell command, after waiting for the number of minutes specified as the delay parameter." Only a date timestamp is recorded ("Only the date is used for the time calculations. The hour is not used."). So any number of missed occurrences collapses to one run, at most one per period. Active jobs are locked against concurrent anacron copies; `-f` forces, `-u` updates timestamps without running; timestamp files are never removed automatically.
- Typical driver: Debian's anacron is activated hourly by cron or a systemd timer and checks for missed jobs.
- Links: [anacron(8), Debian bookworm](https://manpages.debian.org/bookworm/anacron/anacron.8.en.html).

## What the comparables agree on

1. **One durable deadline per unit, re-armed by the handler.** CF and celld permit exactly one outstanding alarm per object/cell; recurrence is a re-arm. systemd/anacron hold a single last-run/deadline record and coalesce multiple misses into one catch-up run.
2. **Schedule state is durable before the external ack.** CF stores alarms in the replicated storage; celld waits for the wake-entry PUT before answering; systemd `Persistent=` writes a timestamp; anacron writes a date-only spool file.
3. **At-least-once delivery with bounded retry + backoff, and the next occurrence outranks a retry.** CF: 2 s exponential, 6 retries. celld: 6 counted failures, 2 s base generic / 4 s cron; `cron_rearm` takes the earlier of retry and next occurrence. systemd/anacron don't retry the schedule — they run once (and systemd leaves an active unit alone).
4. **Catch-up on wake is "once", not per interval.** systemd: one service activation for any number of misses during sleep/power-off. anacron: one run if not run in the last n days. celld: one missed occurrence, then skip; the app catches up from `scheduledTime`. CF: the single alarm slot fires when the object next runs.
5. **Waking a dormant unit on external activity is normal.** E2B `connect()`/autoResume wakes paused sandboxes on SDK/HTTP activity; Fly Proxy starts stopped Machines on a request; CF events and celld requests activate dormant objects/cells. None promises an instant or lossless client wait (Fly explicitly warns requests can fail while start propagates).
6. **Fleet-wide once-only comes from ownership, not an elected scheduler.** celld's reserved cron cell is single-owner via bucket CAS and other nodes forward to the owner. Fly's scheduled start instead relies on the control plane/host and can fail if the host lacks resources.

## Choices still open for pluto

1. **Where trigger state lives** (box record vs host daemon vs both) and which host fires when the owning host is asleep/expired.
2. **Catch-up contract:** one run on wake vs per-interval catch-up; celld's deliberate stance is to expose `scheduledTime` and leave catch-up to the app.
3. **Wake-on-connection:** Fly and E2B both wake on activity, but neither guarantees the client's wait; decide whether a relayed TCP connection resumes a paused box (M0 or later) and what the client sees during microVM restore.
4. **Overlap/queue policy:** celld serializes one event per cell and lets a long handler delay the next occurrence; systemd leaves an already-active unit running; pluto needs an explicit queue/coalesce/drop rule.
5. **Failure surfacing and retry ceiling:** CF/celld abandon after bounded retries; decide how a lost run is surfaced and whether the next schedule silently absorbs it.
6. **Pause vs schedule:** Fly documents that a Machine with a schedule cannot suspend; pluto must decide whether scheduled boxes may pause/hibernate and what a due trigger does to a hibernated vs inactive box.

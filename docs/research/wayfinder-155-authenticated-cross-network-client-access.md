# Authenticated cross-network access for the class demo (#155)

Research performed 2026-10-18 against official project and vendor documentation. This is desk research; connectivity across the actual demo networks and Windows CLI behavior still need hands-on validation.

## Recommendation

Include one opt-in cross-network path in the two-week demo: a native Windows Pluto CLI reaches the Linux host over the owner's Tailscale tailnet, then uses Pluto's documented SSH-based remote CLI path, where `pluto --device` runs the host CLI and the daemon remains behind its Unix socket. Keep LAN access as the baseline, and make the cross-network acceptance check one real command from Windows to the Linux host while the devices are on different networks. Do not build a Pluto relay or expose the daemon's control interface publicly for this demo. [Pluto remote access](../remote-access.md), [ADR 0013](../adr/0013-optional-access-providers.md)

Tailscale has an official Windows client and supports stable tailnet addresses across network changes and firewalls. It attempts a direct encrypted connection and can relay encrypted traffic through DERP when NAT or firewall conditions prevent a direct path. The relay fallback makes CGNAT less likely to block a demo, but performance can be worse, and actual restrictive networks still need to be tested. [Windows install](https://tailscale.com/docs/install/windows), [connect to devices](https://tailscale.com/docs/how-to/connect-to-devices), [connection types](https://tailscale.com/docs/reference/connection-types), [DERP](https://tailscale.com/docs/reference/derp-servers)

For the first demo, use Tailscale for authenticated network reachability and ordinary OpenSSH for SSH user authentication and host-key verification. The tailnet owner enrolls the Windows and Linux devices and permits only the needed host/port in the tailnet policy; the Linux host continues to authorize its SSH user/key. Tailscale SSH can replace key distribution, but it adds host-side SSH policy configuration and is not needed to demonstrate the existing Pluto transport. Tailscale's Personal plan is currently free for individuals, with up to six users and unlimited user devices; the hosted coordination service and DERP fallback remain external dependencies. [Access control](https://tailscale.com/docs/features/access-control), [Tailscale SSH prerequisites](https://tailscale.com/docs/features/tailscale-ssh), [pricing](https://tailscale.com/pricing)

This is feasible in two weeks as a narrow demo because Pluto already documents SSH remote access and Tailscale is an opt-in host integration. Treat that feasibility as an estimate, not a guarantee: the demo must verify one actual Windows/Linux network pair early. The scope should promise reachability plus a fresh CLI operation after a network interruption, not resume an already-running SSH session or attach. Tailscale can re-establish the device path; the SSH transport/application session is a separate connection and must be opened again after it breaks. This distinction is an inference from the documented network and SSH session models; no Pluto-specific reconnect behavior is established by vendor docs. [Pluto remote access](../remote-access.md), [provider implementation](../../internal/provider/tailscale.go)

## The boundary: host control vs selected-service ingress

Pluto needs private access to the Linux host so the Windows CLI can invoke the host-side CLI/daemon through SSH. OpenTunnel provides public ingress to a selected local TCP service. Its documented route is a public TLS hostname bridged to the local route owner; it does not provide tailnet membership, SSH user authorization, or a Pluto control-plane client. OpenTunnel's own README says anyone with the route URL can reach the service and that the route is not authentication. A stock SSH client speaks SSH rather than the TLS/SNI route protocol, so using OpenTunnel for Pluto control would require an additional compatible client adapter and a separate authentication boundary. That last compatibility statement is an inference from OpenTunnel's documented TLS ClientHello routing and local TLS termination. [OpenTunnel README](https://github.com/anomalyco/opentunnel), [server architecture](https://github.com/anomalyco/opentunnel/blob/master/docs/server.md), [trust boundary](https://github.com/anomalyco/opentunnel/blob/master/docs/trust-boundary.md)

Keep OpenTunnel for its existing purpose only: an explicitly selected in-box service whose own authentication remains enabled. Do not route the Pluto daemon/control API through it. The local provider decision already draws this boundary in [ADR 0013](../adr/0013-optional-access-providers.md) and [service connections](../service-connections.md).

### Upstream source drift

The repository's ADR 0013 and earlier M5 research describe an AWS relay as an OpenTunnel dependency. The current official OpenTunnel README/server docs say the hosted server is on Fly.io with PlanetScale and that the AWS relay was replaced by direct server-side TLS ingress. Re-check these operational dependencies before any future OpenTunnel setup instructions; do not copy the old AWS-relay claim into the class-demo spec. The current README lists prebuilt Linux and macOS binaries, not Windows; it does not establish a supported native Windows OpenTunnel client. The Windows demo does not need that client if it uses Tailscale plus OpenSSH. [OpenTunnel README](https://github.com/anomalyco/opentunnel), [OpenTunnel server docs](https://github.com/anomalyco/opentunnel/blob/master/docs/server.md)

Direct SSH and Cloudflare Tunnel are included as alternatives, not required demo branches. A direct endpoint is network-dependent; Cloudflare's path is viable but adds a client binary and account/domain policy steps. A self-operated general relay would add infrastructure, security, and reconnect work that is not justified for this two-week demo.

## Smallest credible demo path

1. Keep the Linux host/daemon and existing SSH-mediated CLI design. On a LAN, prove the normal Windows CLI operation using OpenSSH.
2. Enroll that Linux host and one native Windows device in the host owner's tailnet. Permit only the intended Windows identity/device to reach that host on TCP 22; keep SSH key and host-key verification enabled.
3. From Windows on a separate network, run one read-only Pluto operation and one bounded lifecycle operation through the existing remote CLI path. Disconnect/reconnect the Windows network and prove a **new** CLI command works after Tailscale returns. Do not claim the old SSH/attach session resumed.
4. If the actual network blocks Tailscale's required outbound paths or the demo policy forbids Tailscale accounts, keep LAN acceptance and treat Cloudflare Tunnel + Access as a separately approved fallback; do not silently weaken SSH/auth or expose the daemon publicly.

This recommendation resolves the research question sufficiently for the class-demo spec: specify LAN as baseline and Tailscale-over-SSH as the one supported cross-network demonstration route. It does not require a human choice before the spec can proceed. The host owner still has to enroll/approve the demo devices and provide the account, which is ordinary setup rather than an unresolved architecture decision.
